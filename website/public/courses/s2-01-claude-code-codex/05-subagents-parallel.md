# 1.5 subagent 与并行开发

上一节把上下文讲成了一份有限的预算：会话一开局，系统提示、你的 `CLAUDE.md`、工具列表就先占掉一截，剩下的额度越用越少，用满了就开始"越聊越傻"。你也拿到了一套"长会话不失控"的操作手法。但那套手法治的是"省着花"，这一节要解决的是另一种花法——**有些活它天生就费上下文，省不下来**。

## 一个绕不开的两难

设想两个你迟早会撞上的场景。

第一个：你想让主力 AI 摸清一个陌生模块到底怎么运作，就让它"把 `src/payment` 下面所有文件都读一遍，讲清楚这套支付流程是怎么串起来的"。它老老实实照做了，十几个文件几千行代码哗啦啦全灌进了当前会话。调研报告是拿到了，可你低头一看上下文——预算已经被这堆源码吃掉一大半，接下来真正要动手改代码时，空间捉襟见肘，没聊几轮就触发压缩了。你为了"了解一下"，把整个会话的元气都搭进去了。

第二个：你手头有两个不相干的小功能想同时推进，一个改登录页样式，一个给导出接口加个字段。你在同一个仓库、同一个分支上让 AI 交替改这两处，结果它一会儿动这个文件、一会儿动那个，改到一半你想先提交样式那块，却发现两处改动搅在一起，`git` 状态一团乱，想拆都拆不干净。

这两个场景，一个是"调研污染了正事的上下文"，一个是"多条改动挤在一处互相打架"。它们的解法，恰好就是这一节的两件武器：**subagent** 和 **git worktree**。

## 把活外包给一个"分身"

先说 subagent。名字听着玄，其实就一句话：**它是你主力 AI 派出去干专项活的一个分身，而这个分身有一间自己的、跟主会话完全隔开的工作间。**

关键就在"隔开"这两个字。打个比方：你是项目负责人，手头正忙着一件正事（主会话），这时冒出来一个需要翻一大堆资料的调研任务。你有两种做法。一种是自己把资料全搬到自己桌上翻——桌子瞬间被堆满，正事的摊子被挤没了，这就是前面那个"读十几个文件把上下文塞爆"的下场。另一种做法是：把这个调研任务外包给一个助理，只跟他说"去把支付流程摸清楚，回头给一页纸的结论"。助理在他自己的房间里翻资料、做笔记、堆成山，跟你这边一点不相干；干完了，他只把那一页纸结论递给你。**那一屋子的资料翻动，从头到尾没进过你的桌面。**

subagent 就是这个助理。它读的那十几个文件、中间来回的思考，全发生在它自己独立的上下文里；活干完，回流到你主会话的**只有一小段结论摘要**，那堆源码原文一个字都不占用你的预算。这就是为什么"外包"能治"调研污染"——脏活累活留在分身那间屋子，主会话只收干净的结果。

这里有一个最容易被忽略、却最要命的点，必须单独拎出来讲清楚：

> **subagent 不继承主会话的对话历史。它只拿到你派活时给的那份任务摘要，此外对你俩之前聊过什么一无所知。**

这是把双刃剑，两面都得懂。好的一面前面说了——正因为它不背着你主会话那一大坨历史，它自己那间屋子才是干净、宽敞的，能专心把这一件事做深。坏的一面是：**你不能假设它知道上下文。** 你在主会话里跟 AI 磨了半天才达成的共识、定下的约定、踩过的坑，分身统统不知道。所以派活时，凡是它需要的信息，你都得在任务描述里一次性交代清楚，不能指望它"你懂的"。把它当成一个能力很强、但今天第一天来、对你项目背景一无所知的外援，你就不会派错活。

## 给分身立个规矩：`.claude/agents/`

上面说的是随手派个临时分身。但如果有一类活你反复要外包——比如"每写完一段功能就找人审一遍代码"——每次都现编一段任务描述太啰嗦。这时候就把这个分身**固化成一个文件**，存起来反复用。

做法和 1.3 写自定义命令是同一个路子：在项目里建 `.claude/agents/` 目录，每个 `.md` 文件就是一个预定义的 subagent。文件顶部用 frontmatter 写它的身份配置，正文写给它的"岗位说明书"（也就是它的系统提示）。一个审查代码的分身长这样：

```markdown
---
name: code-reviewer
description: 审查刚写完的代码改动，专找 bug、没覆盖的边界情况和安全隐患。一段功能实现完成后调用它复核。
tools: Read, Grep, Glob
model: sonnet
---

你是一名严格的代码审查员。收到一段代码改动后，按下面几点逐条检查并给出结论：

1. 逻辑是否正确，有没有明显的 bug；
2. 边界情况（空值、越界、并发、异常路径）有没有漏掉；
3. 有没有安全隐患（注入、越权、敏感信息泄露）；
4. 命名、结构是否清晰。

只报你有把握的问题，按严重程度排序。没问题就直说通过，不要为凑数硬挑毛病。
```

frontmatter 里这四个字段，含义直接：

- **`name`**：这个分身的名字，调用时用它指名。
- **`description`**：一句话说清它是干什么的、什么时候该派它上场。这条**特别重要**——主力 AI 正是靠读这句描述来判断"手头这个活要不要转给这个分身"。描述写得越准，它越能在恰当的时机自动把活外包出去。
- **`tools`**：给这个分身开哪些工具权限，逗号分隔。上面这个审查员只需要读代码和搜索，那就只给它 `Read`、`Grep`、`Glob`，不给它写文件的权限——一个审查员本来也不该动你的代码。**按需最小授权**，这个原则 1.3 讲权限时你已经见过。
- **`model`**：指定这个分身用哪个模型，取值是 `sonnet`、`opus`、`haiku`，或者 `inherit`（跟主会话用同一个模型）。审查这种活可以用相对轻量的模型跑，把最强的模型留给主会话干重活。

frontmatter 里够用、也最该先掌握的就是上面这四个字段（`name`、`description`、`tools`、`model`），照着写就能跑；其余可选字段等你有更细的需求时再查官方文档。

写好这个文件，主力 AI 就多了一个随叫随到的审查员。怎么触发它？两条路：一是它会**自动派活**——当你干的事跟某个分身的 `description` 对上了，主力会自己判断"这活该转给 code-reviewer"，把它调起来；二是你**明说**，比如让它"用 code-reviewer 审一下刚才这段改动"。想看看当前有哪些分身可用，或者新建、编辑它们，敲 `/agents` 打开那个交互界面——列出已有分身、新建一个、修改现成的，都在里面操作。显式调用时措辞也很随意，直接用大白话点名"用 code-reviewer 这个 subagent 审一下刚才这段改动"就行，不用记什么特殊语法。

## git worktree：同一个仓库，开好几间工作台

subagent 解决的是"调研别污染上下文"。前面第二个两难——"两个功能挤一处打架"——要靠另一件工具：**git worktree**。

它是什么？一句话：**让你从同一个仓库里，一次切出好几个各自独立的工作副本，每个副本待在自己的分支上，互不干扰。**

想想 `git` 平时的样子：一个仓库、一个工作目录，你同一时刻只能站在一个分支上。想从改样式切去改接口，得先把手头没干完的活提交掉或者塞进 `stash`，再 `git checkout` 换分支——像一张工作台，换活就得先把台面清空。功能一多，光是来回切换、腾挪台面就够烦的，还容易切错、丢东西。

worktree 把这张独一份的工作台变成了**好几张并排的台子**。同一个仓库背后共享同一套提交历史，但你可以给"改样式"开一张台、给"改接口"再开一张台，两张台各自摆在不同的分支上、各自是一套完整的文件副本。你在这张台上改样式改到一半、文件摊着没提交，完全不影响隔壁那张台上改接口——它们是两个独立的目录，物理上就分开了。想同时推两个功能，一功能一张台，谁也别想挤着谁。

建一张新台子，就一条标准 `git` 命令。假设你在练习仓库里，想为"改导出接口"这个功能开一个新工作副本：

```bash
git worktree add ../练习仓库-export -b feature-export
```

这条命令干了两件事：在当前仓库旁边新建一个叫 `练习仓库-export` 的目录（那就是新台子），同时在里面切出并签出一个叫 `feature-export` 的新分支。进到那个目录，你看到的就是一套完整的项目文件，但它站在 `feature-export` 分支上，跟你原来目录里的分支各走各的。

想看看当前一共开了几张台：

```bash
git worktree list
```

功能做完、分支合并回主干之后，把这张台子撤掉：

```bash
git worktree remove ../练习仓库-export
```

## 两件武器合起来用

真正顺手的玩法，是让 subagent 和 worktree**配合着上**。

worktree 给了你好几张物理隔离的工作台，subagent 给了你好几个上下文隔离的分身。把它们叠在一起：给"改样式"那张台配一个专门跑这活的会话、给"改接口"那张台配另一个，两条线并排推进，各自的改动落在各自的分支上、各自的上下文互不串味。你从"一个人守着一张台、一次只能干一件事"，升级成了"同时开好几摊、各摊有各摊的分身在跑"。这就是这一节标题里"并行开发"的实质。

再往深想一层，这两种隔离其实治的是同一类病，只是层面不同。worktree 隔的是**文件层**——两个功能改到的代码物理分家，`git` 状态互不搅和，你想先提交哪个就提交哪个，拆得干干净净。subagent 隔的是**上下文层**——两条任务线各自的思考、各自读进来的资料互不占用，谁也别想把谁的预算吃掉。文件不打架、上下文不串味，两层都隔开了，"同时推进多件事"才真正做得到、而不是名义上并行、实际乱成一锅。这也是为什么这两件工具值得放在同一节讲：它们是"并行"这枚硬币的两面。

## Codex 那边怎么做同样的事

副手 Codex 也能干这两类活，只是抓手不太一样。

"外包子任务"这件事，Codex 的常见做法是给子任务**换一个更快的小模型**去跑——在配置里把某些活指到更轻更快的那类小模型上，重活留给旗舰模型，思路和 Claude Code 给分身指定轻量 `model` 是一个道理：不是所有活都值得动用最强最贵的那颗脑子。审查、检索、跑一遍格式化这类相对机械的活，用小模型又快又省，把旗舰模型的算力留给真正需要深思的主线，整体又快又划算。而"编排一串子任务、批量往外派"，Codex 靠的是 1.1 提过的 `codex exec`——它能非交互地把一个任务跑完、结果流式吐出来，天然适合写进脚本里一条条串起来自动执行。worktree 那部分则完全不分家：它是 `git` 自己的能力，跟你用哪个 AI 工具无关，两边通用。

## 手把手：外包一次审查，再开一条并行分支

概念讲透了，落到你那个练习仓库里各走一遍。

**第一步，造一个 code-reviewer 分身。** 在练习仓库根目录建 `.claude/agents/` 目录，把前面那段 `code-reviewer.md` 原样存进去。存好之后，在会话里敲 `/agents`，你应该能在列表里看到这个新分身，说明它被识别到了。

**第二步，派它上场。** 随便让主力 AI 写一小段带点边界情况的代码——比如给练习仓库写一个"解析分页参数、页码非法就回退到第 1 页"的小函数。写完之后，让它"用 code-reviewer 审一下刚才这段改动"。你会观察到主力把这活转交出去、分身独立跑完、回来给你一份带严重程度排序的审查结论。**这时留意一下上下文：** 分身读代码、逐条检查的过程并没有把大量原文灌进你的主会话，回来的只是那份结论——这就是"隔离"实实在在的好处，你亲眼看一次就记住了。你还可以用 1.4 学过的 `/context` 前后对比一下：让分身审查的这一轮，主会话的上下文占用几乎没怎么涨，因为吃掉预算的那些源码原文，全留在分身那间屋子里了。这跟你直接在主会话里让它"读一遍再审"是两种完全不同的开销，一比就清楚外包省在哪。

**第三步，开一条并行分支。** 回到练习仓库目录，用前面那条命令切出一个新工作台：

```bash
git worktree add ../练习仓库-export -b feature-export
```

进到新目录 `练习仓库-export`，在这里启动一个新的 AI 会话，让它专心干"改导出接口"这一件事。与此同时，你原来的目录还停在主分支上，可以另开一个会话干别的。两个目录、两条分支、两个会话，各推各的。做完之后 `git worktree list` 看一眼、合并分支、再 `git worktree remove` 把台子撤掉。走完这一遍，"并行开发"你就有了肌肉记忆。

## 新手最容易卡的几个点

**卡点一：以为分身知道你俩之前聊过什么。** 这是最高频的坑。你在主会话里聊了半天需求，然后甩给分身一句"按刚才说的审一下"——分身一脸懵，因为它压根没听过"刚才"。**派活时把它需要的背景一次说全**，别用"如上""按之前的约定"这种指代，它接不住。

**卡点二：把 worktree 目录建到仓库里面去了。** 新工作台的目录要建在仓库**旁边**（用 `../` 建到上一级），不要建在当前仓库目录内部，否则它会被 `git` 当成仓库里的一堆文件，一团乱。命令里的 `../练习仓库-export` 就是这个意思——建到平级。

**卡点三：分身工具给多了。** 一个只负责审查的分身，`tools` 里没必要给写文件、跑命令的权限。给多了它就可能"手痒"去动你的代码，越权了。回到 1.3 那个原则：**按这个分身真正要干的活，给最小的一组工具。**

**卡点四：worktree 用完不清理，越堆越多。** 每开一张台都占一份磁盘、留一个分支。功能合并完就顺手 `git worktree remove` 撤掉，`git worktree list` 定期看一眼有没有忘了收的。别让废弃的工作台堆成一片。

**卡点五：什么活都想外包。** subagent 不是万金油。它启动、交接摘要本身有成本，一件三两句就能在主会话里说清的小事，外包出去反而绕。**外包的判断线很简单：这活要读一大堆东西、或要独立深挖、或你想让它别污染主会话——占上这一条再派分身，否则主会话直接干更利索。**

## 总结

这一节给了你两件治"费上下文、怕打架"的武器。

subagent 是把活外包给一个有独立工作间的分身：它读的一大堆文件、来回的思考全留在它自己那间屋里，回流到你主会话的只有一小段结论，调研的脏活污染不了正事的预算。用的时候记牢那条最要命的规矩——**它不继承你的对话历史，只拿你派活时给的摘要**，所以背景信息得一次交代清楚。反复要用的分身就固化成 `.claude/agents/` 下的一个文件，用 `name`、`description`、`tools`、`model` 四个字段定好它的身份，其中 `description` 写得准不准，直接决定主力能不能在对的时机自动把活转给它。

git worktree 则是把独一份的工作台变成好几张并排的台子：同一个仓库切出多个独立副本，一功能一分支，并排推进互不打架。两件武器叠起来用，就是"并行开发"——多张物理隔离的台子，配上多个上下文隔离的分身，你能同时开好几摊而不乱。Codex 那边同样能外包子任务（换个更快的小模型跑）和编排（`codex exec`），worktree 更是 `git` 自带、两边通用。

走到这里，你的练习仓库里应该已经多了一个 `code-reviewer` 分身，你也亲手开过一次 worktree、并排推过两条分支，看清了"隔离"到底省下了什么。但不管是分身还是主会话，它们再能干，眼下也只够得着你本地这个仓库里的文件——连不上你的数据库、在线文档、第三方服务，很多活它"够不着"。下一节 1.6 就来补这块短板：用 MCP 给 AI 接上外部能力，像插插座一样，把它够不到的地方一个个接进来。
