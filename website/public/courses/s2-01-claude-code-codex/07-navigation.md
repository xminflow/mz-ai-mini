# 1.7 大型与陌生代码库导航

上一节你给练习仓库接上了 MCP，AI 从"只能读项目里的文件"升级成了"能连数据库、查文档、够得着外部服务"。到这里，这一阶段该攒的武器基本齐了：一份说清项目规矩的 `CLAUDE.md`、几个把重复流程固化下来的自定义命令、一道拦危险操作的 hook、一套管住上下文别越聊越傻的手法、几个把脏活外包出去的 subagent，还有刚接上的 MCP。这一节不再往仓库里加新东西，而是把这一整套装备，用到它们最该用、也最容易翻车的场景上——接手一个你完全不熟的大代码库。

## 痛点：一个几万行、没人交接的老项目

设想这么个真实场景。你被丢进一个已经跑了三年的项目，几万行代码，前面写它的人早就走了，没有文档、没有交接、README 还停留在第一版。产品经理过来说："这个下单流程有个 bug，你看一下。"你打开仓库，一百多个文件夹在眼前铺开，光是找"下单逻辑到底写在哪"就得翻半天。

这时候你心里会有两种矛盾的冲动。一种是"干脆让 AI 全权处理算了"——把 bug 描述丢给它，让它自己找、自己改。但你又不敢，因为你根本不知道它会动到什么：这么大的项目，牵一发动全身，它自信满满改完了，你却没能力判断它有没有顺手弄坏别的地方。另一种是自己一行行读，可几万行代码读到猴年马月。

问题的根子在于：**面对陌生大库，"直接让 AI 动手"和"完全靠自己读"都是死路。** 前者是把方向盘交给一个不认路的司机，后者是自己下车步行。真正管用的是第三条路——让 AI 帮你快速认路，但方向盘和刹车攥在你手里。这一节讲的就是这条路怎么走。

## 心法：先理解，再动手，小步验证

在讲任何命令之前，先把心法立住，因为陌生大库里翻车，几乎都不是工具不行，而是顺序错了。

这套心法就两句话。

**第一句，先理解再动手。** 越是陌生、越是庞大的代码库，越要忍住"赶紧改"的冲动，先花力气把"这块功能到底怎么串起来的"摸清楚。理解不到位就动手，等于蒙着眼睛拆一台你没见过的机器——拆坏了都不知道坏在哪。这个道理你在小项目里体会不深，因为小项目一眼能看全；可到了几万行的库，"看不全"是常态，理解就成了动手前绕不过去的第一步。

**第二句，小步验证。** 想清楚了也别一次改一大片。把改动切成尽量小的一块块，改一处、立刻验证一处——跑测试、看页面、验接口，确认这一步没问题，再走下一步。陌生库里你对"改这里会不会影响那里"心里没底，小步就是给自己留退路：真出问题，回滚一小步的代价，远比回滚一大片小得多。

这两句话贯穿这一节剩下的全部内容。下面每一个工具、每一步操作，都是在为"先理解、再动手、小步验证"这套顺序服务。

## 第一招：plan 模式，先规划不落手

Claude Code 有一个专门为"先理解再动手"设计的模式，叫 **plan（计划）模式**。它的特点是**只读**——在这个模式下，AI 可以尽情读文件、搜代码、把整块逻辑摸个通透，但它**不会真的去改任何文件、不会执行任何有副作用的命令**。它读完之后，交给你的是一份"打算这么改"的方案，而不是一堆已经改好的代码。

这正好卡在你最需要的那个位置上。面对陌生库，你最怕的就是它"边看边改、看错了也改下去了"。plan 模式把"看"和"改"这两件事强行掰开：先只让它看，看完出方案，方案你审过、点头了，才切回正常模式让它动手。相当于装修前先让工人出一份施工图给你过目，而不是拎着锤子直接上墙。

用法上，你在会话里切到 plan 模式，然后把任务丢给它，比如"下单流程里优惠券不生效，先排查原因、给出修复方案，先别改代码"。它会去读相关文件、顺着调用链找，最后回你一段分析加一份计划：问题大概出在哪个文件的哪段逻辑，打算怎么改，会动到哪几个地方。你看这份计划：方向对，就让它执行；方向不对，就在计划阶段纠正它——这时候纠正的成本几乎是零，因为它还一行代码都没改。

具体怎么切到 plan 模式？两个办法：在会话里按 **Shift+Tab** 循环切换权限模式（default → acceptEdits → plan，多按几下就轮到 plan）；或者启动 Claude Code 时直接带上 `--permission-mode plan` 标志，一进来就在 plan 模式。

这一招和 1.3 讲的权限模式是一套东西——plan 就是那几个权限模式里最保守的一个。当时埋的伏笔，到陌生大库这个场景才真正显出价值：**越不熟的代码，越要先用只读模式把它看明白。**

## 第二招：两级过滤，把探索外包出去

光有 plan 模式还不够。陌生大库还有第二个坑——**上下文会被撑爆**。

回想 1.4 讲的：AI 的上下文窗口是一份有限预算。而"摸清一个陌生大库"这件事，天生就极其费上下文——它得读一大堆文件才能搞明白结构，这些文件内容一股脑塞进当前会话，很快就把预算吃光了。等你真要它动手改的时候，窗口里塞满了探索时读过的、大半跟这次改动无关的文件，它反而"越读越懵"，正事没空间了。

解法是 1.5 学过的那招——**把探索外包给 subagent**。关键在于 subagent 的上下文和主会话是**隔离**的：它读了一百个文件、翻了半天，这些内容留在它自己的上下文里，最后**只把一份结论摘要交回主会话**，中间翻过的那一大堆原始文件不回流。Claude Code 里有个现成的、专门干这个的只读探索分身，你可以把"去搞清楚下单流程都涉及哪些文件、主流程怎么走"这种脏活派给它，它闷头读完，回你一份干净的地图，而不是把整座图书馆搬进你的会话。

于是就有了**两级过滤**这个核心打法：

- **第一级，外包探索。** 让探索分身去"大海捞针"——在几万行里定位相关文件、理清调用关系。这一级读得又多又杂，但污染都留在分身那边。
- **第二级，主会话精准改。** 分身交回一份精炼的地图后，主会话拿着这张地图，只把真正相关的那几个文件读进来，做精准的、小步的修改。

两级一分，主会话的上下文就始终是干净的：它不用亲自趟探索那摊浑水，只拿最后的结论。这就像查案——外勤满城跑访遍所有线人（第一级），回来只给指挥部一份线索汇总（第二级），指挥部不必亲历每一次盘问，照样能据此定下一步动作。

## 第三招：按目录分层的 CLAUDE.md

前面两招解决"这一次改动"的探索问题，但同一个大库你要改很多次。总不能每次都从零摸一遍结构。

这里就轮到 1.2 学的 `CLAUDE.md` 派上大场面了。当时你在项目根目录写了一份，讲的是整个项目的规矩。但对大库来说，光根目录一份不够——一个几万行的库，往往分成好几个模块，每个模块有自己的一套约定（前端目录怎么组织、后端某个服务的接口风格、某个老模块有哪些不能碰的坑）。

Claude Code 支持**按目录分层放 `CLAUDE.md`**：根目录一份管全局，某个子目录里再放一份，只在 AI 读到那个目录下的文件时才追加生效。这样你就能把"探索这个大库时得到的理解"沉淀下来——第一次费劲摸清了下单模块，就在 `order/` 目录下写一份 `CLAUDE.md`，记下"这个模块的主流程从哪个文件进、优惠券逻辑在哪、历史遗留的那个坑要绕开"。下次再改这块，AI 一读到这个目录就自动带上这份地图，不用重新探索。

这是把一次性的探索成果，变成长期资产的关键动作：**每摸清一块，就地写下来。** 探索的钱花一次，往后一直吃利息。

## 第四招：/clear，及时清场

最后一招最简单，却最容易被忘。

1.4 讲过 `/clear`：一键清空当前会话的上下文，等于开一场全新的对话。在陌生大库里，它的用处被放得特别大——因为你在一个大库里，一天可能要在好几件不相干的事之间切换：上午排查下单 bug，下午改用户中心的样式。如果一直在同一个会话里连着干，上午那摊下单相关的文件、讨论、试错，会一直赖在上下文里，等你下午改样式时纯属噪音，还白占预算。

规矩很简单：**任务一切换，先 `/clear`。** 把上一件事彻底清场，让新任务从一张干净的桌子开始。在大库里，一份干净的上下文比什么都值钱——它直接决定 AI 还有没有余力把当前这件事想清楚。

## 手把手：拿一个陌生仓库走一遍

道理讲完，完整走一遍。找一个你**从没读过的开源仓库**当靶子——不用是什么大项目，随便挑一个你感兴趣的中等规模仓库，克隆到本地，进到目录里启动 Claude Code。目标不是真改出个功能，而是把上面四招串成一条流水线，亲手感受一遍"先理解、再动手、小步验证"。

**第一步，plan 模式先规划。** 别急着让它改任何东西。先切到 plan 模式，给它一个只读的探索任务：

```text
先别改任何代码。通读这个项目，说清楚：它是干什么的、用的什么技术栈、代码主要分成哪几块、程序的入口在哪个文件。
```

它会去读一圈，回你一份项目全貌。这一步你就得到了这个陌生库的第一张地图。

**第二步，外包探索摸清一处细节。** 挑一个你想搞懂的小功能，把定位工作外包给探索分身：

```text
去查清楚"用户登录"这个功能都涉及哪些文件，主流程是怎么走的，最后列一份文件清单和调用顺序。
```

分身闷头读完，回你一份精炼的清单。注意这一步读了很多文件，但你主会话的上下文还是干净的——脏活留在了分身那边。

**第三步，小步改一处。** 现在你对这块有谱了，挑一个最小的改动来做，比如给登录失败加一行更清楚的日志。让主会话只读相关的那一两个文件，做这一处修改。改动越小越好——这一步的重点是体会"只碰该碰的、不惊动别的"。

**第四步，立刻验证。** 改完马上验：跑一下这个模块的测试，或者把功能实际跑一遍，确认这处小改动生效了、也没弄坏别的。验过了，这一小步才算数。如果验证没过，就退回上一步，把改动再缩小、再改一次——这正是图里那条黄色虚线画的回路。

走完这四步你会发现，从头到尾你都没"把方向盘交出去"：AI 帮你认路、帮你干最累的探索和最细的改动，但每一个关口——看什么、改哪里、算不算过——都是你在拍板。这就是陌生大库里最稳的节奏。

## 常见坑

**坑一：一上来就让它"把这个 bug 修了"。** 陌生库里最常见的翻车，就是跳过理解直接下命令改。它会很配合地改给你，但你没有能力判断改得对不对、伤没伤到别处。永远先 plan、先探索，再动手。

**坑二：所有事都堆在一个会话里连着干。** 探索、修改、又换个功能，全在同一场对话里滚雪球，上下文越滚越脏，AI 越来越不在状态。切任务就 `/clear`，别舍不得。

**坑三：摸清了却不写下来。** 费半天劲搞懂了一个模块，改完就关会话走人，下次再来又得从零摸一遍。摸清一块就顺手在那个目录写一份 `CLAUDE.md`，把理解钉住。

**坑四：改动贪大。** 一次想改一大片，"反正让它一次都改了"。大库里牵连多，一次改太多，出了问题你根本定位不到是哪一处引起的。宁可多走几个小步。

## 总结

这一节把前面几节攒的装备，用到了它们最该证明自己的地方——一个你完全不熟的大代码库。核心是一套顺序：**先理解，再动手，小步验证。** 落到具体操作，就是四招：用 **plan 只读模式**先规划、只出方案不落手；用 **两级过滤**把费上下文的探索外包给隔离的分身、主会话只拿地图做精准小改；把每次摸清的理解沉淀成**按目录分层的 `CLAUDE.md`**；靠 **`/clear`** 在任务切换时及时清场。四招合起来，就是让 AI 替你认路、而方向盘始终在你手里。

到这里，整个这一阶段也走到了终点。回头看，你从 1.1 一路加到 1.6 的那些配置，其实不是七件孤立的小工具——它们合起来，正好凑成一套"接手陌生项目第一天"的标准动作。把它收成一条清单，就是这门课留给你的东西：

- **先备好工具（1.1）**：主力 Claude Code、副手 Codex，装好、登录、各跑通一次。
- **进项目先写规矩（1.2）**：进到陌生仓库，第一件事是让它 `/init` 出一份 `CLAUDE.md`，把摸到的技术栈、构建命令、测试命令记下来——这份文件从此是所有探索成果的落脚点。
- **架好安全闸门（1.3）**：配上拦危险命令的 hook、收紧权限清单。越是不熟的代码，越要先把"它能干什么、什么得先问你"的边界立起来。
- **管住上下文（1.4）**：`/context` 看用量、`/compact` 压缩、任务切换 `/clear` 清场，让每件事都从干净的桌面开始。
- **外包探索、并行推进（1.5）**：把"大海捞针"式的探索派给上下文隔离的分身，主会话保持干净；多个功能用 worktree 并行，互不打架。
- **接上外部能力（1.6）**：需要连数据库、查文档时，用 MCP 把 AI 够不着的地方接上。
- **合起来，就是这一节（1.7）**：plan 先规划、两级过滤、分层 `CLAUDE.md`、`/clear` 控场，四招拼成"先理解、再动手、小步验证"的安全改动流程。

这套流程不是背下来的教条，是你从今天起每接手一个陌生项目都能照着走一遍的动作。真正的收获也从来不是记住了多少个命令名，而是你现在有了一套**属于自己、能反复复用的 AI 开发工作流**——从选工具、定规矩、设闸门，到管上下文、外包脏活、接外部能力、稳稳导航陌生大库，一条链是通的。往后无论换什么项目、多大的库，把这条链走一遍，你就不再是那个盯着一百个文件夹发怵的人了。
