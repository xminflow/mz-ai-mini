# 1.2 项目级配置：CLAUDE.md 与 AGENTS.md

上一节两个工具都装好了，主力副手也定了下来——Claude Code 当主力，Codex 当副手。现在手里有刀了，这一节开始正式"调教"它。往你第一阶段那个练习仓库里落的第一块真配置，就是这一节要写的东西：一份让 AI 一进项目就懂规矩的说明书。

## 你是不是每天都在重复交代同一件事

先描述一个场景，看看你有没有中招。

你在练习仓库里让 AI 加个功能，它写完了，但用的是你压根没在用的那套写法——你项目里数据库访问全走一个封装好的层，它偏偏直接手写了一段原始 SQL；你项目里跑测试是一条特定命令，它自作主张编了另一条根本不存在的命令去跑，然后卡在那儿报错。你只好停下来，一条条纠正："这个项目数据库要走那个封装层""测试是用这条命令跑的""新文件放这个目录别乱放"。纠正完这次，下次开个新会话，它又忘得一干二净，你又得从头交代一遍。

这不是 AI 笨。是它**根本不知道你项目的规矩**。它刚被拉进你的项目，就像一个能力很强但第一天入职的新同事——技术底子厚，可你们团队用什么框架、测试怎么跑、代码风格是什么、文件该往哪放，这些"只有你们内部才知道"的约定，没人告诉它，它只能靠猜。猜对了算走运，猜错了你就得返工。

那现实里新同事入职，怎么解决这个问题？发一份入职手册。把"团队用什么技术栈、代码怎么写、命令怎么跑、目录怎么摆"白纸黑字写清楚，新人照着看一遍就上手了，不用老员工一遍遍口头交代。

给 AI 配项目配置，干的就是这件事：**把项目的规矩写进一份文件，AI 每次进项目自动读一遍，从此不用你反复口述。** 这份文件在 Claude Code 里叫 `CLAUDE.md`，在 Codex 里叫 `AGENTS.md`。这一节就带你把两份都写出来，放进练习仓库。

这也是整个工作流里**第一个、也是性价比最高的杠杆**——花十几分钟写一份说明书，换来往后每次对话都少踩一堆坑。

## CLAUDE.md：放在项目里的一份说明书

先说主力这边的 `CLAUDE.md`。

它本质上就是一个普通的 Markdown 文本文件，放在你项目根目录下，文件名就叫 `CLAUDE.md`。里面写什么？写你希望 AI 干活时时刻记住的事——用什么框架、构建和测试怎么跑、目录怎么组织、代码风格有什么讲究、有哪些坑千万别踩。Claude Code 每次在这个项目里启动，都会自动把这份文件的内容读进去，当成"背景知识"揣着，然后再开始干你派的活。

你不用死记怎么从零写。Claude Code 提供了一个命令帮你生成初稿：

```
/init
```

在你的练习仓库目录里启动 `claude`，敲下这条命令，它会自己把你的项目扫一遍——看你用了哪些依赖、有哪些脚本命令、目录长什么样——然后生成一份初版 `CLAUDE.md` 草稿。这份草稿不会完美，但省掉了你对着空文件发呆的第一步，后面你手工补几笔关键的就成型了。

## 一份配置，其实分了三层

这里有个新手常忽略、但特别重要的机制：`CLAUDE.md` 不是只有一份，它分三层，从"最通用"到"最私人"依次叠加。

用生活里的例子类比：这就像一家公司的规章。总部有一套所有分公司通用的员工守则，你所在的这个项目组有一份组内公约，你个人桌上还贴着几张只对自己有用的便利贴。三层规矩同时管着你，越靠近你个人的、越具体，遇到冲突时以更贴身的那层为准。

`CLAUDE.md` 的三层正是这个结构，自上而下：

- **用户级**：文件在 `~/.claude/CLAUDE.md`。这层写的是**你个人跨所有项目的通用偏好**——比如"回答尽量简洁""注释用中文"。它不属于任何单个项目，你机器上所有项目都会读到它。相当于跟着你个人走的那套习惯。
- **项目级**：文件就是项目根目录下的 `./CLAUDE.md`。这层写**这个项目专属的规矩**——技术栈、构建测试命令、目录约定。它会进 git、跟着仓库走，所以是**团队共享**的：你的同事拉下这个仓库，AI 读到的是同一份项目规矩，全组一致。
- **本地级**：文件是项目里的 `./CLAUDE.local.md`。这层写**只对你自己、不该塞给全组**的东西——比如你本地那套跟别人不一样的临时调试路径。它通常会被加进 `.gitignore`，**不进 git**，纯属你个人在这个项目里的私货。

加载顺序是自上而下依次读进来，**后加载的那层追加到前面之上**：先读通用的用户级，再读项目级，最后读最贴身的本地级。碰到规矩冲突，越靠后、越具体的那层说了算——就像你桌上的便利贴能盖过总部守则里那条不适用的。

三层里，你现在最该动手写的是**项目级**那份 `./CLAUDE.md`——它跟着练习仓库走，是这一节的主角。用户级那份等你手上项目多了、发现自己每次都在重复交代同一句个人偏好时，再抽出来放进去也不迟。举个例子帮你分清哪句话该放哪层：像"数据库访问走 `repositories` 封装层"这种只对当前项目成立的规矩，属于项目级；而"回答别啰嗦、直接给结论"这种跟哪个项目无关、你在所有项目里都想要的习惯，才该放用户级。判断标准就一句话：**换个项目还成立吗？成立就往上一层放，不成立就留在项目级。**

为什么要费劲分这三层、不干脆全塞进一份？因为它们的"归属"不同。项目级要进 git 给全组共用，你不能把个人口味强加给同事；用户级跟着你个人的机器走，换项目也带着；本地级是你在这个项目里的临时私货，不该污染仓库。分层的本质是**让每条规矩待在它该待的作用域里**，各归各位、互不干扰。

## @import：别把同一段内容抄两遍

写着写着你会碰到一个尴尬：项目里很多约定其实已经写在别的文档里了。比如根目录的 `README` 已经讲了怎么启动项目，你的架构说明文档里已经写清了目录职责。总不能把这些又原样抄进 `CLAUDE.md` 一遍——抄一遍就意味着以后改一处得记得改两处，迟早对不上。

`CLAUDE.md` 给了个办法：**用 `@` 把别的文件引进来**。在 `CLAUDE.md` 里写一行：

```
详见 @README
```

Claude Code 读到 `@README` 时，会把 `README` 文件的内容原地展开、一起读进上下文。你也可以引项目里更深的文档：

```
架构约定见 @docs/architecture.md
```

这里的相对路径是**相对于写这行字的那个文件**来算的，不是相对你当前所在目录，这点记牢，不然容易引错。

有个细节要留意：如果你把 `@某某` 写在了代码块里（三个反引号围起来的那种），或者写在了行内反引号里，它**不会**被展开——那种情况下 `@` 只当普通文字看待。这其实是好事：你在 `CLAUDE.md` 里举例、演示某段命令时，不用担心里面的 `@` 被误当成引用触发。

`@import` 的价值就是**一处维护、处处生效**：`README` 改了，`CLAUDE.md` 里引它的地方自动跟着变，你不用两头同步。

## 关键一步：它是"软约束"，不是"硬规则"

这一节最容易被忽略、但你必须现在就建立的认知是——**`CLAUDE.md` 里写的东西，是"软约束"，不是"硬规则"。**

什么意思？`CLAUDE.md` 的内容会被读进 AI 的上下文，成为它干活时的背景参考，AI 会**尽量遵循**。注意是"尽量"。它更像你贴在同事桌上的一张提醒便利贴——绝大多数时候对方会照着做，但便利贴本身没有强制力，万一对方那天状态飘忽、或者任务一复杂把这条给忘了，它照样可能没照做。

举个具体的：你在 `CLAUDE.md` 里白纸黑字写了"任何情况下都不要删除数据库文件"。大多数时候 AI 会规规矩矩绕开。但"写进 `CLAUDE.md`"这个动作本身**并不能从物理上拦住它**——它读到了、理解了、通常也会遵守，可这跟"它绝对做不到"是两码事。软约束靠的是 AI 的自觉，不是一道真正锁死的门。

那真要"锁死"某件事怎么办？——那就不是 `CLAUDE.md` 该干的活了，得靠**硬门**：一道无论 AI 怎么想都绕不过去的强制关卡。这正是下一节 1.3 的主题。你现在先把这颗种子埋下：**`CLAUDE.md` 负责"告诉它该怎么做"（软），1.3 的 hook 和权限负责"从技术上拦住它不许那么做"（硬）。** 两者分工不同，缺一不可，别指望在 `CLAUDE.md` 里写一句"请务必"就把危险操作彻底堵死。

顺着这个分工，正好说清另一件事：`CLAUDE.md` 和另一份配置 `settings.json` 各管什么。

## CLAUDE.md 管"怎么做"，settings.json 管"能不能做"

Claude Code 里有两份配置文件，新手很容易搞混，其实分工很清爽：

| 对比项     | CLAUDE.md              | settings.json         |
| ------- | ---------------------- | --------------------- |
| 管什么     | 行为指导：怎么写代码、跑什么命令、目录怎么放 | 技术配置：权限、hooks 等       |
| 形式      | 自然语言写的 Markdown 说明     | 结构化的 JSON 配置项         |
| 约束力     | **软约束**——进上下文，AI 尽量遵循  | **强制执行**——由工具本身把关，绕不过 |
| 类比      | 贴在桌上的提醒便利贴             | 门禁刷卡机                 |
| 本节 / 后续 | 本节就写                   | 1.3 专讲                |

一句话记住：**`CLAUDE.md` 是"讲道理"，`settings.json` 是"立规矩"。** 讲道理靠对方自觉，立规矩靠机器把关。这一节先把"道理"讲清楚（写好 `CLAUDE.md`），"规矩"下一节再立。

## 手把手：给练习仓库写出第一份 CLAUDE.md

概念铺完，动手。目标是让练习仓库里真真切切多出一份能用的 `CLAUDE.md`。

**第一步，用 `/init` 生成初稿。** 切到练习仓库目录，启动 `claude`，敲：

```
/init
```

它扫完项目会生成一份 `CLAUDE.md` 草稿，通常已经把你的技术栈、部分脚本命令自动填进去了。先别急着满意——`/init` 能扒出来的，只有那些"写在代码和配置文件里、机器能自己看到"的东西；而真正容易让 AI 猜错的，恰恰是那些**没写在任何文件里、只存在你脑子里**的约定：比如"数据库必须走封装层别手写 SQL""这个目录是废弃的别往里加东西"。这些机器扫不出来，只能靠你手工补。所以别把 `/init` 的产出当终点，它只是帮你省掉从空白起步的力气。

**第二步，手工补上五类关键条目。** 打开生成的 `CLAUDE.md`，照下面五块逐一补齐、修准。这五块是一份全栈应用配置的骨架，缺哪块 AI 就在哪块上瞎猜：

1. **技术栈**：前端、后端、数据库分别用什么，版本别含糊。
2. **构建 / 运行命令**：怎么把项目跑起来，一条条写清楚。
3. **测试命令**：跑测试到底敲哪条命令——这条最容易被 AI 猜错，务必写死。
4. **目录约定**：哪类文件放哪个目录，新代码该往哪落。
5. **代码风格**：命名、注释、数据访问必须走哪层封装之类的硬性讲究。

下面是一份针对全栈应用的可抄模板，把方括号里的内容换成你练习仓库的真实情况，直接就能用：

```markdown
# 项目说明

一个全栈待办应用：[前端] + [后端] + [数据库]。

## 技术栈

- 前端：[React + Vite + TypeScript]
- 后端：[FastAPI（Python 3.12）]
- 数据库：[PostgreSQL，通过 SQLAlchemy 访问]

## 构建与运行

- 装依赖（前端）：`pnpm install`
- 装依赖（后端）：`uv sync`
- 启动前端开发服务：`pnpm dev`
- 启动后端开发服务：`uv run uvicorn main:app --reload`

## 测试

- 跑后端测试：`uv run pytest`
- 跑前端测试：`pnpm test`
- 提交前请确保上面两条都通过。

## 目录约定

- 前端页面组件放 `src/pages/`，通用组件放 `src/components/`
- 后端接口按业务模块分目录，放 `app/api/`
- 数据库模型统一放 `app/models/`

## 代码风格

- 所有数据库访问必须走 `app/repositories/` 下的封装层，禁止在接口里手写原始 SQL。
- 新增接口必须配套写测试。
- 注释用中文，只在逻辑不直观处写，别给一眼看懂的代码加废话注释。
```

补完存盘。到这儿，练习仓库里就有了第一份像样的项目配置。

**第三步，让 AI 跑个活验收一下。** 别只是写完就走，要亲眼确认它"现在懂规矩了"。在同一个仓库里，派它一个刚好会踩到你写的约定的小任务，比如"给待办列表加一个按创建时间排序的接口"。观察两点：它跑测试时用的是不是你 `CLAUDE.md` 里写的那条命令？它访问数据库时是不是老老实实走了你要求的封装层，而不是手写 SQL？如果是——说明这份说明书真被读进去、生效了。这就是配置带来的实感：同样一句话派活，配置前它靠猜，配置后它照着你的规矩来。

有个小对照能让你更直观地感受落差：如果你愿意，可以先在一个**没写 `CLAUDE.md`** 的空目录里派同样一个任务，看它怎么瞎猜命令、怎么随手写 SQL；再回到配好的练习仓库派一遍。两次输出摆一起，你会立刻明白这份文件的分量——它不是可有可无的装饰，而是把 AI 从"每次重新认识你的项目"变成"一进门就熟门熟路"的那道开关。往后每写一个新项目，第一件事顺手就是给它配上 `CLAUDE.md`，会变成你的肌肉记忆。

## 副手这边：写一份等价的 AGENTS.md

主力配好了，顺手把副手 Codex 那份也配上，往后交叉验证时它一样懂你项目的规矩。

Codex 读的配置文件叫 `AGENTS.md`。它跟 `CLAUDE.md` 是同一个思路——放在项目里、用自然语言写项目约定、启动时自动读——而且 `AGENTS.md` 是一个**跨工具的开放标准**，好几家 AI 编程工具都认它，通用性更好。

层级上它跟 `CLAUDE.md` 的分层同理，也是"越通用在上、越具体在下、具体压过通用"（就是前面那张图右半边画的）：从**仓库根目录到你当前工作目录，一层层的 `AGENTS.md` 会被逐层拼接起来，越靠近叶子（越贴近你此刻所在目录）的那份，覆盖力越强**。此外还有个全局级，放在 `~/.codex` 下，作用相当于 Claude 那边的用户级。

好在内容你几乎不用重写：把刚才那份 `CLAUDE.md` 的正文**原样复制**成一份 `AGENTS.md` 放进项目根目录就行——技术栈、命令、目录、风格这些约定，两个工具通用，不因换工具而变。写完同样让 Codex 在仓库里跑个小任务，确认它也照规矩来。

要提醒一句两边的对应关系，别搞混：`AGENTS.md` 对应的是 `CLAUDE.md`（都是"讲道理"的软约束）；而 Codex 那边"立规矩"的技术配置，放在另一份叫 `config.toml` 的文件里（在 `~/.codex/config.toml`），模型选哪个、审批和沙箱怎么设都在那儿——它对应的是 Claude 的 `settings.json`，不是 `AGENTS.md`。换句话说，两个工具都遵循同一套分工：**一份自然语言说明书讲道理（软），一份结构化配置立规矩（硬）。** config.toml 里那些审批、沙箱的门道，跟 Claude 的 `settings.json` 一样，都留到 1.3 一起讲。

## 新手最容易卡的几个点

**卡点一：把 `CLAUDE.md` 写成了长篇大论。** 生怕漏讲，恨不得把项目每个细节都塞进去，结果写成一篇几千字的文档。这反而帮倒忙——`CLAUDE.md` 每次都要占用 AI 的上下文空间（这块是 1.4 的正题），太长既挤占空间又让重点被淹没。原则是**只写"AI 不知道就会猜错"的关键约定**，一眼能看懂、不写也不会错的别往里塞。宁可精简。

**卡点二：把该锁死的事只写进了 `CLAUDE.md`。** 比如把"绝不能删生产数据库"当成一条 `CLAUDE.md` 规矩写完就安心了。前面强调过：那是软约束，靠自觉，拦不死。真正危险、绝不容许出错的操作，得等 1.3 用 hook 和权限来立硬门。`CLAUDE.md` 里写当然可以写，但别把它当成安全保障。

**卡点三：`CLAUDE.local.md` 忘了进 `.gitignore`。** 本地级那份是你的私货，要是没加进 `.gitignore`，一提交就把你个人的临时配置推给了全组，既尴尬又可能干扰别人。写完本地级配置，顺手确认它在 `.gitignore` 里。

**卡点四：`@import` 路径引错。** 记住相对路径是**相对写引用的那个文件**算的，不是相对你敲命令时所在的目录。引完最好让 AI 跑一下、确认它真读到了被引文件的内容，别默认它一定生效。

## 总结

这一节没讲多深的技术，但装上了整套工作流的第一块、也是回报最高的一块地基：**把项目的规矩写下来，一次喂给 AI，从此不用反复口述。**

回顾几条要点。项目配置就是给 AI 的一份入职手册——Claude Code 叫 `CLAUDE.md`，Codex 叫 `AGENTS.md`，思路完全一样。它分三层叠加，从跨项目的用户级、到进 git 的项目级、再到只属于你的本地级，越具体的越靠下、冲突时越优先；`@import` 让你把已有文档引进来、一处维护处处生效；`/init` 帮你生成初稿，但真正值钱的是你手工补上的那五类关键约定——技术栈、构建命令、测试命令、目录约定、代码风格。两个工具还共享同一套分工：一份自然语言说明书"讲道理"（`CLAUDE.md` / `AGENTS.md`，软约束），一份结构化配置"立规矩"（`settings.json` / `config.toml`，硬执行）。

到这里，你的练习仓库里应该已经躺着一份真实的 `CLAUDE.md` 和一份对照的 `AGENTS.md`，AI 派活时也确实照着你的规矩来了。

但这一节末尾反复敲的那记警钟，正是下一节的入口：`CLAUDE.md` 是软约束。你在里面写一百遍"请注意别删数据库"，AI 通常会听，可一旦哪次它没听——文件真删了，说"请注意"是拦不住的。光讲道理不够，有些事必须立一道机器把关、谁都绕不过去的硬门。1.3 就来立这道门：用自定义命令把重复流程固化成一条 `/命令`，用 hook 在 AI 动手前架起一道自动拦截的关卡，再用一份权限清单划死"什么绝对不许碰"。软约束交代完了，接下来是硬规则。
