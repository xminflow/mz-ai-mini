# 1.4 上下文工程实战

上一节把配置、命令和 hook 都落到了你的练习仓库里：项目规矩写进了 `CLAUDE.md`，重复流程固化成了自定义命令，危险操作也有 hook 帮你拦着。工具这台"车"已经调校得很顺手了。可你多半很快会撞上另一个问题——车是好车，但开着开着就"犯迷糊"了。这一节就来解决它。

## 越聊越傻，到底是怎么回事

你八成已经遇到过这个场景：一个任务跟 AI 来回聊了很久，前半程它又快又准，可越往后越不对劲。你让它改 A，它顺手把你半小时前刚否掉的 B 方案又搬了回来；你问一个明明前面交代过的细节，它答得驴唇不对马嘴；甚至你说"就按刚才那个思路来"，它一脸茫然地问你"哪个思路"。明明是同一个模型、同一个仓库，怎么聊到后面就像换了个笨的？

先说结论：这不是模型突然变蠢了，也不是你哪句话说错了。真正的病根，是它的"工作记忆"被塞满、被污染了。要讲清楚这件事，得先讲清楚 AI 记东西的地方到底有多大、里面都装了些什么。

## 把上下文想成一份花得很快的预算

AI 每次回你话，都不是凭空回的——它会把"当前这一整段对话能看到的所有文字"一起读进去，再基于这些内容作答。这个"它一次能看进眼里的全部文字"有个名字，叫**上下文窗口（context window）**。关键在于：**它是有上限的**。就像一块固定大小的白板，写满了就写不下了。

最好的理解方式，是把这块白板想成**一份有限的预算**。你可能以为这份预算一开局全归你支配，其实不是——**在你敲下第一句话之前，它已经被扣掉了一大块**。扣在哪了？

- **系统提示**：工具出厂自带的一大段说明书，告诉模型"你是谁、能调用哪些工具、该怎么干活"。这段你看不见，但它一直占着预算。
- **你的 `CLAUDE.md` 和记忆**：上一节你精心写的项目规矩，每次对话都会被读进来陪着你——这正是它"懂你项目"的原因，代价就是占一块预算。
- **工具列表**：每一个它能调用的工具（读文件、跑命令、搜索……）都有一份说明挂在上下文里，工具越多，这块越大。接了 MCP 之后（1.6 会讲）这块还会更鼓。
- **对话历史**：你和它之间来回说的每一句话、它读过的每一个文件内容、跑过的每一条命令和输出——**全都堆在这里，而且只增不减**。

真正被你"聊"出来的，其实只有最后这一块。前面三块是固定开销，开局就扣走了。所以你实际能用的预算，从一开始就比你以为的要少。

现在"越聊越傻"就好解释了。随着你和它聊得越来越久，"对话历史"这块只涨不落——你贴进去的报错、它读过的整个文件、每一次试错的往返，全都堆在里面。堆到一定程度，会出两种麻烦。

一种是**挤占**：预算见底，早期那些真正重要的交代（比如你一开始定的技术选型）被后面一大堆琐碎往返稀释、淹没，模型的注意力被拉散，自然就"忘"了。另一种更隐蔽，叫**上下文污染**：你中途否掉的错误方案、一次跑失败的死胡同、一段贴错的代码，这些"垃圾"并不会自动消失，它们照样占着预算、还在持续影响模型的判断。于是你才会看到那个最典型的症状——**它把你早就否掉的方案又端了回来**，因为那个被否的方案，在它眼里和你采纳的方案一样，都还明晃晃地摆在上下文里，它分不清哪个才作数。

所以"上下文工程"这四个字，说白了就是一件事：**主动管理这份预算，别让它被撑爆、被污染。** 这不是什么高深技巧，而是你从今天起每天都要有的习惯。工具给了你四个趁手的抓手，一个一个来。

## 四个抓手：看、压、换、还有它自己来

### 抓手一：`/context`——先学会看预算

管钱的第一步是知道钱花哪了。在 Claude Code 的会话里敲：

```text
/context
```

它会给你一份当前上下文的用量明细，把前面那张预算条里的每一段——系统提示、`CLAUDE.md`、工具列表、对话历史各占了多少、总共用掉了多大比例——摊开列给你看。

<!-- 截图: /context 命令的实际输出，展示各段 token 占用与总用量百分比 -->
![/context 输出的上下文用量明细](/courses/s2-01-claude-code-codex/img/context-usage.png)

你要养成的习惯是：一个任务聊到感觉"它开始有点跟不上了"，别急着骂它笨，先敲一次 `/context`。看一眼余量还剩多少、对话历史是不是已经涨成了大头。这一眼，就是你判断"该压缩、该清空、还是该干脆重开"的依据。看不见用量就凭感觉操作，跟闭着眼开车没区别。

### 抓手二：`/compact`——把历史压缩成摘要

如果你看完 `/context`，发现对话历史确实很鼓，但**当前任务还没干完、还得接着聊**，这时候用 `/compact`：

```text
/compact
```

它做的事是：把前面那一长串对话历史读一遍，**总结成一段精炼的摘要**，然后用这段摘要替换掉原来那一大坨原文。任务的来龙去脉、已经定下的关键决策都保留在摘要里，但那些啰嗦的往返、试错的过程被大幅压掉了。压缩完你会看到余量一下子回来一大截，模型也重新变得利索。

更好的用法是给它指个重点。压缩时你可以顺带告诉它"这次压缩要重点保留什么",比如:

```text
/compact 重点保留登录接口限流相关的改动和最终采纳的方案
```

这样它在总结时就会优先把你点名的那部分留全，把无关的枝节压得更狠。你正做的是"改登录限流"，就让它盯着这条主线压，别把力气浪费在保留那些早就跑偏的岔路上。

写法上不用记任何特殊格式：`/compact` 后面直接跟一句自然语言指令就行（像上面那样 `/compact 重点保留…`），不需要 `focus:` 之类的关键字前缀。

### 抓手三：`/clear`——换任务就清空

`/compact` 是"任务没变、只是历史太长"时用的。但还有另一种情况：**你要开始一件全新的、和刚才八竿子打不着的活了**。比如你上午一直在调登录接口，下午想让它去改一个完全不相干的邮件模板。

这时候别用 `/compact`——把登录接口那一大段历史"压缩"着带进邮件模板的任务里，纯属拖后腿，那些内容对新任务毫无用处，还占着预算。正确的做法是直接清空：

```text
/clear
```

它会把对话历史整个抹掉，让你回到一块干净的白板（`CLAUDE.md`、工具这些固定开销还在，那是每次都需要的）。新任务从零起步，预算全满，注意力也不会被上一件事的残留干扰。

记住这条铁律：**任务切换，就 `/clear`。** 别嫌麻烦、别为了"省事儿"把好几个不相干的任务全塞进同一个会话里连着聊——那是把上下文主动往污染里推。清空的成本几乎为零，换来的是每个新任务都在满血状态下起步。

### 抓手四:auto-compact——它自己兜底,但别指望它

前面三个都是你主动出手。还有一个是工具自动来的:当你的上下文快要触到那个约 200K 的上限时,Claude Code 会自动触发一次压缩,业内叫 **auto-compact**。它做的事和你手动 `/compact` 类似——**把完整的对话历史压成一段结构化的摘要**,腾出空间让会话能继续下去,而不是硬邦邦地撞上上限、卡死。

这个兜底是好事,但你**不能依赖它**,原因有两个。

一是它压缩的**时机由不得你**。它在逼近上限时才动手,而那个时候你的上下文往往已经被撑得又满又乱、污染早就发生了——它是在"快出事了"才来救场,不是替你未雨绸缪。

二是自动压缩**会丢东西,而且丢什么你不完全可控**。压缩的本质是"把长历史概括成短摘要",概括就意味着取舍。一些具体的细节、一些没被判断为"关键"的往返、某些嵌套的规则约定,可能在这个过程里被简化掉、留不下来。等你后面突然需要那个被丢掉的细节,它已经不在上下文里了,你只能重新交代一遍。

所以正确的姿态是:**把 auto-compact 当安全气囊,而不是刹车。** 安全气囊是真出事时保命的,但没人靠撞车来停车。你该做的是在它自动触发之前,就用 `/context` 盯着用量、用 `/compact` 主动压、该 `/clear` 就 `/clear`——把方向盘攥在自己手里。

## 有时候,最好的操作是"重开一局"

上面四个抓手都是在**一个会话内部**做文章。但有一类问题,在会话内部怎么折腾都不划算,最干脆的解法是**开一个全新的会话**。

什么时候该重开?一个很实用的判断:当你发现**这个会话已经被带偏、绕进了死胡同**——比如你和它为一个 bug 纠缠了几十个来回,试了七八种都不对,整个上下文里堆满了失败的尝试和互相矛盾的猜测。这种时候上下文已经"脏"到 `/compact` 都救不太回来了,因为那些污染早就渗进了每一次往返。与其在一锅浑水里继续搅,不如推倒重来:开个新会话,把你**这一路摸清楚的有效结论**(比如"已经排除了是数据库的问题、大概率出在缓存")重新、干净地讲一遍,让它在一块白板上重新开始。你会惊讶于它一下子又变聪明了。

再进一步,这背后其实是一条更重要的工作方式:**把大任务拆成一串小会话,别用一个超长会话硬扛。** 一个"重构整个订单模块"的大活,与其从头到尾泡在同一个会话里聊到天荒地老、上下文越来越浑,不如拆开——第一个会话专门理清楚现状和方案,第二个会话专门改数据层,第三个会话专门改接口层,每个小会话进去时都是干净预算、目标单一。任务边界清晰,上下文自然就干净。这个"拆小"的思路,到 1.5 讲 subagent 时你会看到更彻底的版本。

## 副手那边:Codex 怎么管会话

你的副手 Codex 在会话管理上是另一套设计,顺带对照着理解一下,交叉验证时不至于抓瞎。

Codex 的会话是可以**恢复(resume)**的。你在终端里跑的对话不是关掉就没,它能把之前的会话接着续上,让你从上次断的地方继续。尤其是它那条非交互的 `codex exec`(前面 1.1 提过,把结果流式吐到标准输出、适合塞进脚本的那个),同样支持恢复之前的会话上下文继续往下跑——这在写自动化流程时很有用,一个长任务分几段接力执行,后一段能接着前一段的上下文。具体到命令,恢复会话用 `codex exec resume`(想直接接最近一次可以加 `--last`);子命令和参数随版本会有微调,以 `codex exec --help` 为准。

心智模型是相通的:不管哪个工具,上下文都是有限、会脏、需要主动管理的资源。命令名不一样、恢复会话的姿势不一样,但"别让它被撑爆、任务切换要隔离干净"这条底层道理,两边完全一致。

## 手把手:压一次给你看

光讲不练记不住,拿你的练习仓库真跑一遍。假设你正让 Claude Code 改登录接口,已经来回聊了一阵子。

**第一步,看用量。** 敲 `/context`,读那份明细。重点看两个数:总用量到了百分之多少、对话历史那段是不是已经明显比其他段大。假设你看到用量已经过半、历史是大头——这就是该压的信号。

**第二步,带重点压一次。** 因为你手上的活是登录限流,就让压缩盯着这条主线:

```text
/compact 保留登录限流的最终方案和已改动的文件,其余压缩
```

它会跑一小会儿,然后回你一句压缩完成的提示。

**第三步,对比前后。** 压完立刻再敲一次 `/context`。你会看到对话历史那段明显瘪了下去、剩余余量涨了回来。下面这张图就是这一压的效果——同一条预算条,压缩前后摆一起看:

跑完这一轮,你就完整摸过了"看→压→换"这条链子。剩下的就是把它变成肌肉记忆。

## 长会话不失控:一份可抄进笔记的 checklist

把这一节的操作收拢成一份清单,抄进你的笔记,或者干脆写进练习仓库的 `CLAUDE.md` 里当团队约定。往后每次长会话,对着它做就不会失控:

```text
长会话不失控 checklist
□ 开工先想清楚这一个会话只干这一件事,别混任务
□ 感觉 AI 开始跟不上,第一反应先敲 /context 看用量,别凭感觉
□ 任务没变、但历史很鼓 → /compact,并带上本次要保留的重点
□ 换一件不相干的活 → 直接 /clear,别把旧历史拖进新任务
□ 会话已绕进死胡同、污染太重 → 别抢救,开新会话把有效结论重讲一遍
□ 大任务提前拆成几个目标单一的小会话,别用一个超长会话硬扛
□ auto-compact 只当安全气囊,别等它自动触发才想起管上下文
```

这份清单不长,但它是你从"工具用户"迈向"能长期驾驭 AI 的人"的分水岭。会不会管上下文,直接决定了你跟 AI 协作到第三个小时还顺不顺。

## 常见坑

**坑一:把 `/compact` 当成 `/clear` 用。** 换任务时图省事用 `/compact`,以为"压一压就干净了"。压缩只是把旧历史缩短,它还在,还占预算、还可能干扰新任务。任务切换认准 `/clear`,别用压缩糊弄。

**坑二:压缩时不给重点,压完发现关键的没了。** 光敲 `/compact` 不带任何指示,它只能按自己的判断取舍,可能恰好把你最在乎的那段决策概括没了。养成习惯:压缩时顺手点一句"重点保留 X",把主线钉住。

**坑三:死等 auto-compact 兜底。** 一路不管不顾聊到工具自动压缩,那时候上下文早就又满又脏,自动压缩还会丢掉你没来得及保护的细节。主动管理永远优于被动兜底。

**坑四:该重开时舍不得重开。** 和一个 bug 缠斗几十回合、上下文已经烂成一锅粥,还硬要在原会话里继续,只会越缠越乱。沉没成本别舍不得——把摸清的结论拎出来,新会话干净重来,往往几步就通。

## 总结

这一节解决的是一个几乎每个人都会撞上、却很少有人真去管的问题:会话一长,AI 就"越聊越傻"。病根不在模型,而在它的上下文窗口——一份开局就被系统提示、`CLAUDE.md`、工具列表占掉一截的**有限预算**,剩下的余量会被只增不减的对话历史一点点吃光,还会被你否掉的方案、失败的试错悄悄污染,于是它开始忘事、答非所问、把你早否掉的方案又端回来。

管住它,靠四个抓手:`/context` 看清预算花在哪,`/compact`(带上重点)把冗长历史压成摘要、任务没变时腾余量,`/clear` 在换任务时清空隔离,auto-compact 只当逼近上限时的安全气囊、绝不主动依赖。再往上一层:会话绕进死胡同就干脆重开一局、把有效结论干净重讲;大任务提前拆成几个目标单一的小会话,别用一个超长会话硬扛。副手 Codex 那边命令名不同、会话能 resume,但"上下文是有限、会脏、要主动管"这条底层道理两边一模一样。

到这里,你的练习仓库里除了配置、命令和 hook,又多了一份"长会话不失控" checklist——这是你能长期、稳定驾驭 AI 的真功夫。不过你可能已经隐约感到一个矛盾:有些活天生就吃上下文,比如"把整个大目录读一遍做调研",光是读完就能把主会话的预算撑爆,正事反而没空间了。与其让主会话被这种脏活拖垮,不如把它**外包出去**——下一节 1.5 就来讲 subagent:派一个上下文完全隔离的"分身"去干调研这种重活,它读一堆文件把自己撑爆都没关系,回流到你主会话的只有一小段干净结论。顺带还会讲怎么用 worktree 开好几条并行分支同时推功能,互不打架。
