# 2026-10-21 全量发布记录

## 范围与验收

本仓库现有生产服务为官网、AI 营子站和后端。管理站尚无生产入口，不新增部署；其他工程的生产容器不属于本次发布。使用本地 Ubuntu WSL、Linux 文件系统及本机 Docker 构建，服务器仅加载镜像、运行候选实例、健康检查、切换和回滚。所有镜像记录摘要，生产部署必须使用候选验收的同一镜像。

验收要求：后端全量测试通过；模板固定包和 ZIP 清单一致；生产构建成功；本地镜像启动、数据库只读检查、关键接口与主站/模板双语页面通过；服务器候选验证通过后切换；Git 提交与 origin/dev 一致。

## 数据升级边界

开发环境修正新库初始化快照。生产部署禁止运行此初始化 SQL，也不回填生产数据。

新库路径：在隔离空数据库执行 server/docker/postgres/init/0002_init_schema.sql，先验证结构、30 条迁移登记和关键业务表，再启动后端。SQL 使用事务、IF NOT EXISTS 及迁移登记冲突忽略；重复执行须在同一目标版本的隔离新库验证，不能用作任意历史数据库升级工具。存在 app 角色时授予既有迁移规定的表/序列权限；开发环境未创建此角色时输出 NOTICE，由数据库所有者访问。

生产实查：schema_migrations 只有 0001-0012 登记，但官网账号、会员、报告、工单等后续结构已存在，说明迁移记录与实际结构脱节；camp_accounts 与 camp_membership_orders 尚缺。禁止直接运行全量迁移器，因为历史 0022 包含删除报告数据、0027 包含会员等级回填，0015 涉及删除旧密码字段。此次不补写这些历史迁移登记，不删除兼容字段。

后续用户明确要求并确认：仅清空本项目生产 app 库全部业务数据，保留表结构与其他项目数据库。因此最终使用 api/migrations/releases/20261021_reset_app_business_data.sql，明确校验库名为 app 后，清空 public 下除 schema_migrations 外的业务表并重置序列；不使用 CASCADE。同时复用 0029、0030 创建 6 张 camp 表、索引和权限，只登记这两项迁移。此前纯新增方案仍留作兼容工具，本次执行的是已授权的清空方案。

执行前停止官网后端及后端候选写入，在服务器 release 目录生成权限受限的完整自定义格式 pg_dump 备份，核验目录清单、完整解码与 SHA256；备份不下载到本机。保存结构及迁移登记。先在本地隔离副本验证样本数据被清空、表结构和迁移记录保留，再执行生产事务。

执行顺序：本地构建与测试 → 生产结构/行数快照 → 备份确认 → 显式升级事务 → 新表、权限、迁移登记及旧表行数验证 → 服务器候选后端（禁用后台扫单）只读验证 → 切换后端、AI 营、主站 → 公网验收。升级设置 5 秒锁等待、60 秒语句超时，失败立即回滚事务。应用切换失败恢复旧镜像，新增表保留以保护切换后可能产生的数据，旧版本忽略新增表，不做删表式回滚。历史迁移记录的全面治理另行处理，不能伪称已完整登记 30 项。

回滚：生产保留原容器和镜像，停止新容器后恢复原容器及自动重启策略；本次没有生产数据回滚步骤。新库初始化失败由事务回滚，修复后在隔离空库重试；若需回退初始化版本，应删除并重建本次专用测试库，不能删除业务库。旧应用与现有生产结构兼容性保持不变。
